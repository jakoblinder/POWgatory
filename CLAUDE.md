# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

POWgatory expands one `run.yaml` into a b2luigi task graph that runs a multi-stage POWHEG-BOX campaign on Slurm, or locally. `README.md` is the user reference for the config schema, CLI, run directory layout and known limitations. This file covers what you need to know to change the code.

## Setup and commands

POWgatory needs an unreleased b2luigi fork: the `powgatory` branch of `jakoblinder/b2luigi`, which provides `submission_type` (`single`/`array`/`mpi`), grouped parameters (`grouping=True`) and the handling of stuck and lost Slurm jobs. With b2luigi from PyPI, `submission_type` is silently ignored. `powgatory` is the head of `slurm_resubmission`, a PR stacked on `slurm_array_submission` (the upstream PR belle2/b2luigi#6); a fix goes on the branch it belongs to. `luigi` is pinned to a GitHub commit in `pyproject.toml`, because no luigi release supports Python 3.14 yet. Develop against both checkouts installed in editable mode, POWgatory first:

```bash
pip install -e /path/to/POWgatory           # Python 3.11-3.14; pulls b2luigi from GitHub and the pinned luigi
pip install -e /path/to/b2luigi             # powgatory branch; replaces the GitHub copy
```

pip only applies the luigi pin when POWgatory is part of the command. Installing b2luigi first, or with `--force-reinstall`/`--upgrade`, resolves luigi from PyPI, which on 3.14 means the broken luigi 3.6.0 (`No module named 'pkg_resources'`).

```bash
powgatory -c run.yaml                # build the graph and submit
powgatory -c a.yaml b.yaml           # several independent configs (POWHEGMultiConfigWorkflow)
powgatory -c run.yaml --dry-run      # list enabled stages; --dry-run is also passed to b2luigi
```

Arguments the CLI does not recognize are passed through to b2luigi. Setting `resources.batch_system: local` (globally or per stage) runs branches as local subprocesses, and `sinfo` is then not queried. `powgatory/config/example.yaml` is the starting point for a run config.

The repo has no test suite and no lint configuration. `pytest`, `black` and `flake8` appear only in the `[dev]` extras.

## Layout

- `cli.py` parses arguments, builds the root task and calls `b2luigi.process`. When imported, it monkey-patches b2luigi's `SlurmProcess.start_job` so that there are at least 2 s between `sbatch` calls. It takes the number of workers from `--workers` or `job_settings.workers`, and sets luigi's resource `local_cores` (`job_settings.local_parallel_tasks`, `auto`: `free_cores()`), of which each local `POWHEGStage` branch takes one (`POWHEGStage.resources`). The resolved number stays out of the config dict, because it differs from node to node and the config is hashed into every task ID. `--clean` (`clean_run_directory`) takes the run-directory locks, moves everything in `run_dir` except `KEPT_ON_CLEAN` (`powheg.sif`, `run_backups`) into `run_backups/<timestamp>/`, and a `log_dir` outside `run_dir` into its `logs/`, then exits before validation and b2luigi.
- `config.py` holds `POWHEGConfig`, a dict-like wrapper. It deep-merges `run.yaml` over `config/config_default.yaml`, fills each stage's and analysis's `resources`/`powheg_parameters` key by key from the top-level blocks, turns every `merge_method` into a list, and validates the stages and analyses.
  - `stages:` holds only the POWHEG stages (the keys in `config_default.yaml`); `analyses:` holds named analyses of the stage-4 events. Inside the tasks an analysis is a stage whose `stage` parameter is its name, so names of stages and analyses must not overlap. `stage_config(config, stage)` (and `POWHEGBaseTask.stage_config`) returns the settings of either; `stage_configs(config)` all of them, stages first; `analysis_names(config)` the analyses. Use these for anything an analysis task also reaches; `config["stages"]` is fine in code only stages 1-4 run.
  - `validate_stages_and_analyses` runs right after the merge: it refuses unknown stage keys (also the `stages.lhef`/`stages.pythia` of configs before 2.6), and analyses without every key in `ANALYSIS_KEYS` (`lhef` and `pythia` get them from the defaults, others have none) or with a name that is not `[A-Za-z0-9_]+`, starts with `stage`, is `p<N>` or a directory in `run_dir`. Those name rules keep `stage_code`, the log names `<name>-s<seed>.log` and `POWHEGStageTimings._log_files` (glob `<name>-*.log`) apart from the stages and from other analyses.
  - `slurm_partitions()` (`sinfo --exact`, `scontrol show partition`) and `slurm_config()` (`scontrol show config`) are cached module functions, queried once per process, because the Slurm controller limits requests per user. `slurm_config()` accepts the output when it has the four settings POWgatory reads, also if `scontrol` exits with 1 because the controller ping at its end failed.
  - `validate_partitions`, called by `cli.py` only in the process that starts the run, checks every Slurm stage against the partitions: name, time limit, memory per node (`mem`, for mpi times `slurm_tasks_per_node`) against the nodes and `MaxMemPerNode`, and `array` stages on a cluster with `MaxArraySize` 0.
  - `max_grouping_size: auto` stays in the config dict. `POWHEGStage.max_grouping_size` resolves it with `auto_grouping_size(slurm_submissions(config))`: the smallest of the largest job array and the largest MPI job of each partition over the config's Slurm stages, one value for all stages (luigi registers one group size per task family). Only luigi's worker in the main process reads it, so batch jobs never run `scontrol`.
  - Seeds per node are cores, not CPUs, where Slurm has `CR_ONE_TASK_PER_CORE` (Viper); `MaxTasksPerNode` only caps them.
- `framework.py` contains the base classes and the naming helpers `stage_code` (`p1-x2`), `job_code` (`p1-x2-s7`, a group `p1-x2-s1to10`) and `stage_name` (`stage1-grid2`, the key in `timings.yaml`). `POWHEGBaseTask` defines the `stage`/`grid_iteration` (-1 outside stage 1)/`config` parameters, path helpers, container setup and `link_stage_input`. `POWHEGWrapperTask` is the base for wrapper tasks.
  - Both replace luigi's task ID by `readable_task_id`: `<family>_<task_label()>_<luigi's hash of the parameters>`, e.g. `POWHEGStage_p1_x2_s7_6206baca65`. Batch jobs look their task up by this ID, so a label may depend on nothing but the parameters.
  - Both print themselves with `short_repr`: the config by its file, a group of seeds as ranges (`branch_id=1-5,8`).
  - A task that does not use an inherited parameter redefines it with `significant=False` (`POWHEGPresubmit`, `POWHEGWeightCorrection`), so that it is left out of the ID and the name. `config` is a `SharedDictParameter`: all tasks of a config share one frozen dict and one JSON string, instead of a copy each, which with many configs in one process filled the memory. Task IDs are the same as with a plain `DictParameter`.
- `tasks.py` contains all concrete tasks and the stage DAG.
- `ub_correction.py` computes the upper bound correction factors from the stage-4 counters files, for the analyses and as command-line tool.
- `grid_contributions.py` reads powheg.input like `powheginput.f` and returns the contributions whose grids POWHEG combines in stage 3 (the switches of `bbinit.f`/`pwhg_init.f`), for `stage3_fullgrid`'s `contributions: auto`.
- `merge.py` merges histogram files (`.top`) like `mergedata` (byte-identical output, methods 1-6), streaming one file at a time; used by `POWHEGMerge` and as command-line tool.
- `config/` and `scripts/` are shipped inside the package. A new runtime file must be added to `[tool.setuptools.package-data]` in `pyproject.toml`, or it won't be installed.
- `.claude-plugin/marketplace.json` and `claude-plugin/` make the repository a Claude Code marketplace with the plugin `powgatory`, whose skill `claude-plugin/skills/powgatory/SKILL.md` tells Claude how to use POWgatory. Users only get a changed skill when `version` in `claude-plugin/.claude-plugin/plugin.json` is raised. Keep the skill in line with the CLI, the config options and the error messages.
- `build/` is a stale setuptools artifact. Edit `powgatory/`, not `build/lib/`.
- The version is `__version__` in `powgatory/__init__.py`. Raise the minor number in every commit that adds a feature, option or stage, and the patch number in a commit that fixes a bug. A new version changes every task ID (see below), so batch jobs that were submitted before the change and start after it fail. Don't change it while a run from this installation has jobs queued.

## Stage DAG

Each stage, and each stage-1 grid iteration, runs this chain of tasks:

`POWHEGStageSetup` → `POWHEGCreateSymlinks` → `POWHEGStage` × `ntasks` → `POWHEGStageTimings`

1. `POWHEGStageSetup` writes `<stage_code>-powheg.input` (`p<N>[-x<G>]`, or `stage3_fullgrid`) by patching the template with the stage's `powheg_parameters`.
2. `POWHEGCreateSymlinks` points `powheg.input` and `pwgseeds.dat` in `run_dir` at this stage's files.
3. `POWHEGStageWrapper` fans out one `POWHEGStage` per seed, with the `branch_id`s from `stage_seeds` (1 to `ntasks`, except with the grid combination, see below). Each `POWHEGStage` runs `scripts/run_program.sh` via `_run_program`, optionally inside Apptainer.
4. `POWHEGStageTimings` parses the job logs into `timings.yaml`.

`POWHEGPresubmit` runs once per run directory, before any stage: every `POWHEGCreateSymlinks` requires it. It points `powheg.input` at the input of stage 1, grid iteration 1 (its requirement `POWHEGStageSetup`) and then runs `job_settings.presubmit`, because the script may read `powheg.input` (e.g. couplings). The link tasks then point `powheg.input` at their own stage's input.

`POWHEGStageTimings` is the join point between stages. The next stage, or the next stage-1 grid iteration, requires the previous stage's timings task. `POWHEGWorkflow` requires the timings task of the highest enabled stage, and `POWHEGMerge` of stage 2 and of every enabled analysis; with `merge_method: 0` (`NO_MERGE`, which `POWHEGConfig` turns into `[]`; it turns every `merge_method` into a list of methods) it requires an analysis's timings task instead of its merge. The dependency on the previous stage is coded twice, in `POWHEGCreateSymlinks.requires` and in `POWHEGStage.requires`, so change both together. Stages must run strictly one after another: they all run in the same `run_dir` and share the `powheg.input`/`pwgseeds.dat` symlinks.

The optional grid combination `stage3_fullgrid` sits between stage 2 and stage 3. It runs stage-3 seeds 1 to `contributions` (`grid_combination_seeds`): `get_stage_number` gives 3, so it writes `parallelstage 3` and produces the outputs of stage 3. In POWHEG-BOX-RES's `bbinit.f`, seed k starts combining the grids of contribution k into a fullgrid file. Stage 3 then requires its timings task and runs only the seeds after it (`stage_seeds`). That split is needed because luigi runs a task it scheduled as incomplete without checking `complete()` again; only grouped Slurm submissions skip complete branches. `POWHEGConfig.__init__` gives the stage stage 3's `powheg_parameters` and refuses its own. It replaces `contributions: auto` by the count from `grid_contributions.py`, which is computed again in every batch job from the same files. `stage_code` keeps the stage name, so its logs (`stage3_fullgrid-s<seed>.log`) and timings entry stay apart from stage 3's `p3-*`.

The analyses (`analyses:` in the config, e.g. `lhef` and `pythia`) run after stage 4, all at the same time, each in its own directory `<run_dir>/<name>/` with its own `executable`:

`POWHEGStageTimings(stage4)` → `POWHEGWeightCorrection` (once, only if an analysis has `weight_correction`) → `POWHEGAnalysisSetup(stage)` → `POWHEGAnalysis` × stage 4's `ntasks` → `POWHEGStageTimings(stage)`

- `POWHEGWeightCorrection` writes the factors of every seed into `ub_corrections.yaml` (`ub_correction.correction_factors`, the logic of POWHEG-BOX's `FindReweightFromCounters.py`), so that they are computed only once for all analyses.
- `POWHEGAnalysisSetup` (a `POWHEGStageSetup`) writes `<name>/<seed>-powheg.input` from the template, the analysis's `powheg_parameters` and the seed's factors, and links the event files and `link_files` in. It resolves `link_files` before writing anything, because its outputs would otherwise count as complete after a failure.
- `POWHEGAnalysis` (a `POWHEGStage`) gives `run_program.sh` the event file as 5th argument; the script then passes the seed and the event file on stdin. The programs read `<seed>-powheg.input` only because their directory has no `powheg.input`, and they take everything before `events` in the event file name as prefix of their outputs, hence the relative links instead of `../pwgevents-*.lhe`. Its `output()` has one alternative set per seed string and `.top` (one weight) or `-W1.top` (several weights, `pwhgtopout`) of the analysis's `histogram` pattern (`histogram_name`, with `{seed}`).

`POWHEGMerge(stage)` (a `POWHEGStage` with one branch and the stage's resources) requires `POWHEGStageTimings(stage)` and merges the histogram files of stage 2 or an analysis per weight and per method in `merge_method` with `merge.merge_histograms`. The name pattern is `histogram_name` (an analysis's `histogram`, `pwg-{seed}-NLO` for stage 2); the weights are found at run time from seed 1's files. `complete()` is false while the timings task is incomplete, and true without any files (stage 2 without `testplots 1`). It has its own `job_name` and log dir (`<stage>-merge`). Its `batch_job_is_hung()` returns False: it overrides the one inherited from `POWHEGStage`, which b2luigi would otherwise call and which would read the POWHEG log of the stage's seed 1.

## Invariants that are easy to break

- **The config dict must be reproduced exactly inside batch jobs.** Each job runs `<config python> -m powgatory --config_file <file> <b2luigi args>` from the submit-time `cwd` (see `executable_prefix`, `executable`, `task_cmd_additional_args` and `working_dir` on `POWHEGStage`). b2luigi then rebuilds the whole task graph in the job and looks the task up by `task_id`. Because `config` is a hashed `DictParameter`, every value in the dict has to come out identical in the job. That includes `cwd` and `python` (from `sys.executable`). Otherwise the job fails with "task id ... does not exist in the locally reproduced task graph". Nothing queried from Slurm may go into the dict: the partition table (`slurm_partitions()`) and `scontrol show config` (`slurm_config()`) are cached module functions, read only by the process that starts the run (partition validation in `cli.py`, `POWHEGStage.partition_info`/`tasks_per_node`/`max_grouping_size`/`slurm_settings`), so batch jobs, and every rank of an MPI job, send no request to the Slurm controller. The same goes for `version`, which is `__version__` with dots replaced by hyphens, so a version bump changes every task ID. `POWHEGConfig.__init__` has side effects (it creates directories and prints the config), and these run again in every batch job, so it must not write files that other jobs read.
- **Jobs get the submitting `PATH`.** `POWHEGStage.slurm_settings` submits with `--export=PATH` (`SLURM_EXPORT` in `config.py`), so jobs find `apptainer` (and the Python of `config["python"]`) where the submitting shell found them; Slurm adds the login environment of the node. `cli.py` sets `SBATCH_EXPORT` to the same value before `b2luigi.process`, because `sbatch` prefers it over the submit file and MPCDF sets it to `NONE` in every login shell.
- **Completion is based on files, not exit codes.** This includes the stage inputs: `POWHEGStageSetup` is complete as soon as its input file exists, and `POWHEGCreateSymlinks` as soon as its marker does, so `powheg_parameters` changed later are not applied in an existing `run_dir` (a known limitation, in the README). `POWHEGStage.output()` returns several alternative sets of POWHEG output files: 4- and 5-digit seeds (`seed_strings`, used for every seed in a file name), and for stage 1 also the `pwggridinfo-*` variant. `complete()` accepts any one set. `_wait_for_stage_output` and `_quarantine_stale_outputs` both work from `output()`. The latter moves leftovers from a previous attempt into `incomplete_run_backups/` before POWHEG runs again. For stage-3 seeds (grid combination and stage 3), this includes the `*-fullgrid.lock` files that contain the seed's own number (`_own_fullgrid_locks`). POWHEG's `pwhg_exit` deletes its locks, so such a lock can only be left by a killed earlier attempt of the same seed. Locks of other seeds must never be touched, because those seeds may still be running. Rerunning `powgatory` resubmits only the branches that are incomplete.
- **Log markers.** `_run_program` writes `<Started-POWHEG:<job_code>=<iso time>>` and `<Finished-POWHEG:...>` into each branch log, and `POWHEGStageTimings._parse_log_timing` parses them. Change both together. `POWHEGStageTimings.complete()` also checks that its dependencies are complete, so an entry left in `timings.yaml` by an older run does not count.
- **b2luigi settings are task properties.** `POWHEGStage` provides b2luigi settings (`batch_system`, `submission_type`, `max_grouping_size`, `slurm_settings`, `result_dir`, `task_file_dir`, `job_name`, ...) as properties that read the per-stage config, because `b2luigi.get_setting` looks at the task first. Add new per-stage settings the same way. The setup, symlink, presubmit and timings tasks set `batch_system = "local"`.
- **Stuck and lost jobs are handled by b2luigi** (`slurm_resubmission`). `POWHEGStage` supplies `slurm_max_resubmissions` (`job_settings.retries`), `slurm_completing_grace` (`job_settings.completing_grace`), `slurm_hung_check_after` (`job_settings.hung_start_minutes`) and the hook `batch_job_is_hung()`, which reads the branch's POWHEG log. b2luigi's `SlurmJobState` counts a job in COMPLETING or lost as successful if the branch's outputs are complete. Otherwise it resubmits a lost job at once, and a job in COMPLETING after `completing_grace` seconds. It asks `batch_job_is_hung()` once, `hung_start_minutes` after it first saw the job RUNNING, and cancels and resubmits a hung job. `POWHEGBaseTask.retry_count` is 1, so luigi never retries, and a POWHEG failure is never rerun automatically.
- `complete()` and `_wait_for_stage_output` share `_complete_output_set`: a branch is complete only if every file of one output set exists and is non-empty. On a POWHEG error, `_run_program` moves the branch's outputs aside, because `pwhg_exit` writes the counters file also on failure.
- **Paths keep their symlinks.** `POWHEGConfig.__init__` makes the config's paths absolute with `os.path.abspath` (joins with the cwd, removes `..` by name), not `Path.resolve()`: on Viper `/u` is a symlink to `/viper/u1`, and the container has the home only as `$HOME` (`/u/<user>`). Only `config_file` and the run-directory locks in `cli.py` are resolved, because they are compared with `getcwd()` or must identify a directory uniquely. `POWHEGStage._container_binds` binds every directory the program needs; a new file that a program reads in the container must lie in one of them.
- `setup_container` runs inside every batch job. `POWHEGPresubmit` calls it once beforehand, so a local `container_image` is copied and a registry image pulled to `<run_dir>/powheg.sif` before any stage runs: when the parallel jobs of a stage copied it themselves, jobs started apptainer on a half-written copy. Keep the call in `POWHEGStage.run`, for runs whose seeds do not share one run directory. With `job_settings.copy_container_image: false`, a local image is used in place, so that many runs share one image.
- `cli.py` locks every run directory in the main process (not in batch jobs, which carry `--batch-runner`), so that two POWgatory processes never share a run directory. A lock is one byte of `<parent>/.powgatory-run-dirs.lock`, at an offset from the sha256 of the run directory's name (POSIX byte-range locks, `fcntl.lockf`), so all run directories of one parent share one open file: an `flock` per run directory needed one open file each, and 900 configs exceeded the login shell's soft limit of 1024. Closing any descriptor of a lock file releases all its locks, so nothing else may open these files.
- `branch_id` is a `BatchIntParameter(grouping=True, grouping_function=sorted)`. In a grouped submission it is a sorted tuple of seeds, so build names from it with `format_branch_id` or `job_code` (e.g. `s1to5_8`).
- `addweights` exists in the config schema and validation but has no tasks yet.
