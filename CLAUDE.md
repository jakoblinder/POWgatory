# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

POWgatory expands one `run.yaml` into a b2luigi task graph that runs a multi-stage POWHEG-BOX campaign on Slurm, or locally. `README.md` is the user reference for the config schema, CLI, run directory layout and known limitations. This file covers what you need to know to change the code.

## Setup and commands

POWgatory needs an unreleased b2luigi fork: the `powgatory` branch of `jakoblinder/b2luigi`. It is `slurm_array_submission` (the upstream PR belle2/b2luigi#6) plus `slurm_resubmission`, a second PR stacked on it. `slurm_resubmission` starts with the tenacity commit (allows tenacity 9, which luigi ≥ 3.8 needs), then handles held, transient and lost Slurm states, jobs that hang in COMPLETING and jobs that hang in RUNNING. `powgatory` points at the same commit as `slurm_resubmission`, with no merge commit. Keep the branches separate: a fix goes on the branch it belongs to, `slurm_resubmission` is rebased onto `slurm_array_submission` when that changes, and `powgatory` is then moved to the new head of `slurm_resubmission`. The fork provides `submission_type` (`single`/`array`/`mpi`) and grouped parameters (`grouping=True`). With b2luigi from PyPI, `submission_type` is silently ignored. `luigi` is pinned to a GitHub commit in `pyproject.toml`, because no luigi release supports Python 3.14 yet. Develop against both checkouts installed in editable mode, POWgatory first:

```bash
pip install -e /path/to/POWgatory           # Python 3.11-3.14; pulls b2luigi from GitHub and the pinned luigi
pip install -e /path/to/b2luigi             # powgatory branch; replaces the GitHub copy
```

pip only applies the luigi pin when POWgatory is part of the command. Installing b2luigi first, or with `--force-reinstall`/`--upgrade`, resolves luigi from PyPI, which on 3.14 means the broken luigi 3.6.0 (`No module named 'pkg_resources'`).

```bash
powgatory -c run.yaml                # build the graph and submit
powgatory -c a.yaml b.yaml           # several independent configs (POWHEGMultiConfigWorkflow)
powgatory -c run.yaml --dry-run      # list enabled stages; --dry-run is also passed to b2luigi
```

Arguments the CLI does not recognize are passed through to b2luigi. Setting `resources.batch_system: local` (globally or per stage) runs branches as local subprocesses, and `sinfo` is then not queried. `powgatory/config/example.yaml` is the starting point for a run config.

The repo has no test suite and no lint configuration. `pytest`, `black` and `flake8` appear only in the `[dev]` extras.

## Layout

- `cli.py` parses arguments, builds the root task and calls `b2luigi.process`. When imported, it monkey-patches b2luigi's `SlurmProcess.start_job` so that there are at least 2 s between `sbatch` calls. It takes the number of workers from `--workers` or `job_settings.workers`, and sets luigi's resource `local_cores` (`job_settings.local_parallel_tasks`, `auto`: `free_cores()`), of which each local `POWHEGStage` branch takes one (`POWHEGStage.resources`). The resolved number stays out of the config dict, because it differs from node to node and the config is hashed into every task ID.
- `config.py` holds `POWHEGConfig`, a dict-like wrapper. It deep-merges `run.yaml` over `config/config_default.yaml`, fills each stage's `resources`/`powheg_parameters` key by key from the top-level blocks, and validates the stages; `validate_partitions` checks them against `sinfo`, called by `cli.py` only in the process that starts the run. `slurm_partitions()` (`sinfo --exact` and `scontrol show partition`) and `slurm_config()` (`scontrol show config`) are cached module functions, queried once per process, because the Slurm controller limits requests per user and hundreds of configs each querying made the commands fail. `validate_partitions` also checks the memory per node (`mem`, for mpi times `slurm_tasks_per_node`) against the partition's nodes and `MaxMemPerNode`. `max_grouping_size: auto` stays in the config dict; `POWHEGStage.max_grouping_size` resolves it with `auto_grouping_size(slurm_submissions(config))`, the smallest of the largest job array (`slurm_max_array_size()`) and the largest MPI job of each partition (`slurm_max_mpi_size()`) over the config's Slurm stages, the same value for every stage (luigi registers one group size per task family). Seeds per node are cores, not CPUs, where Slurm has `CR_ONE_TASK_PER_CORE` (Viper); `MaxTasksPerNode` only caps them. Only luigi's worker in the main process reads that property, so batch jobs never run `scontrol`.
- `framework.py` contains the base classes. `POWHEGBaseTask` defines the `stage`/`grid_iteration`/`config` parameters, path helpers, container setup and the naming helpers `stage_code` (`p1-x2`) and `job_code` (`p1-x2-s7`). `POWHEGWrapperTask` is the base for wrapper tasks. `config` is a `SharedDictParameter`: all tasks of a config share one frozen dict and one JSON string, instead of a copy each, which with many configs in one process filled the memory. Task IDs are the same as with a plain `DictParameter`.
- `tasks.py` contains all concrete tasks and the stage DAG.
- `ub_correction.py` computes the upper bound correction factors from the stage-4 counters files, for the analysis stages and as command-line tool.
- `grid_contributions.py` reads powheg.input like `powheginput.f` and returns the contributions whose grids POWHEG combines in stage 3 (the switches of `bbinit.f`/`pwhg_init.f`), for `stage3_fullgrid`'s `contributions: auto`.
- `merge.py` merges histogram files (`.top`) like `mergedata` (byte-identical output, methods 1-6), streaming one file at a time; used by `POWHEGMerge` and as command-line tool.
- `config/` and `scripts/` are shipped inside the package. A new runtime file must be added to `[tool.setuptools.package-data]` in `pyproject.toml`, or it won't be installed.
- `.claude-plugin/marketplace.json` and `claude-plugin/` make the repository a Claude Code marketplace with the plugin `powgatory`, whose skill `claude-plugin/skills/powgatory/SKILL.md` tells Claude how to use POWgatory. Users only get a changed skill when `version` in `claude-plugin/.claude-plugin/plugin.json` is raised. Keep the skill in line with the CLI, the config options and the error messages.
- `scrap.py` holds ideas for future work, such as grid combination and addweights. It is not imported anywhere, but keep it: don't delete it or treat it as dead code.
- `build/` is a stale setuptools artifact. Edit `powgatory/`, not `build/lib/`.
- The version is `__version__` in `powgatory/__init__.py`. Raise the minor number in every commit that adds a feature, option or stage, and the patch number in a commit that fixes a bug. A new version changes every task ID (see below), so batch jobs that were submitted before the change and start after it fail. Don't change it while a run from this installation has jobs queued.

## Stage DAG

Each stage, and each stage-1 grid iteration, runs this chain of tasks:

`POWHEGStageSetup` → `POWHEGCreateSymlinks` → `POWHEGStage` × `ntasks` → `POWHEGStageTimings`

1. `POWHEGStageSetup` writes `<stage_code>-powheg.input` (`p<N>[-x<G>]`, or `stage3_fullgrid`) by patching the template with the stage's `powheg_parameters`.
2. `POWHEGCreateSymlinks` points `powheg.input` and `pwgseeds.dat` in `run_dir` at this stage's files.
3. `POWHEGStageWrapper` fans out one `POWHEGStage` per seed, with the `branch_id`s from `stage_seeds` (1 to `ntasks`, except with the grid combination, see below). Each `POWHEGStage` runs `scripts/run_program.sh` via `_run_program`, optionally inside Apptainer.
4. `POWHEGStageTimings` parses the job logs into `timings.yaml`.

`POWHEGPresubmit` runs once, before any `POWHEGStage`.

`POWHEGStageTimings` is the join point between stages. The next stage, or the next stage-1 grid iteration, requires the previous stage's timings task. `POWHEGWorkflow` requires the timings task of the highest enabled stage, and `POWHEGMerge` of stage 2, `lhef` and `pythia` if enabled; with `merge_method: 0` (`NO_MERGE`) it requires an analysis stage's timings task instead of its merge. The dependency on the previous stage is coded twice, in `POWHEGCreateSymlinks.requires` and in `POWHEGStage.requires`, so change both together. Stages must run strictly one after another: they all run in the same `run_dir` and share the `powheg.input`/`pwgseeds.dat` symlinks.

The optional grid combination `stage3_fullgrid` sits between stage 2 and stage 3. It runs stage-3 seeds 1 to `contributions` (`grid_combination_seeds`): `get_stage_number` gives 3, so it writes `parallelstage 3` and produces the outputs of stage 3. In POWHEG-BOX-RES's `bbinit.f`, seed k starts combining the grids of contribution k into a fullgrid file. Stage 3 then requires its timings task and runs only the seeds after it (`stage_seeds`). That split is needed because luigi runs a task it scheduled as incomplete without checking `complete()` again; only grouped Slurm submissions skip complete branches. `POWHEGConfig.__init__` gives the stage stage 3's `powheg_parameters` and refuses its own. It replaces `contributions: auto` by the count from `grid_contributions.py`, which is computed again in every batch job from the same files. `stage_code` keeps the stage name, so its logs (`stage3_fullgrid-s<seed>.log`) and timings entry stay apart from stage 3's `p3-*`.

The analysis stages `lhef` and `pythia` (`ANALYSIS_STAGES` in `config.py`) run after stage 4, both at the same time, each in its own directory `<run_dir>/<stage>/`:

`POWHEGStageTimings(stage4)` → `POWHEGWeightCorrection` (once, only if a stage has `weight_correction`) → `POWHEGAnalysisSetup(stage)` → `POWHEGAnalysis` × stage 4's `ntasks` → `POWHEGStageTimings(stage)`

- `POWHEGWeightCorrection` writes the factors of every seed into `ub_corrections.yaml` (`ub_correction.correction_factors`, the logic of POWHEG-BOX's `FindReweightFromCounters.py`), so that they are computed only once for both stages.
- `POWHEGAnalysisSetup` (a `POWHEGStageSetup`) writes `<stage>/<seed>-powheg.input` from the template, the stage's `powheg_parameters` and the seed's factors, and links the event files and `link_files` in. It resolves `link_files` before writing anything, because its outputs would otherwise count as complete after a failure.
- `POWHEGAnalysis` (a `POWHEGStage`) gives `run_program.sh` the event file as 5th argument; the script then passes the seed and the event file on stdin. The programs read `<seed>-powheg.input` only because their directory has no `powheg.input`, and they take everything before `events` in the event file name as prefix of their outputs, hence the relative links instead of `../pwgevents-*.lhe`. Its `output()` has one alternative set per combination of a name pattern in `HISTOGRAM_NAMES` (a list per stage, with `{seed}`), a seed string and `.top` (one weight) or `-W1.top` (several weights, `pwhgtopout`).

`POWHEGMerge(stage)` (a `POWHEGStage` with one branch and the stage's resources) requires `POWHEGStageTimings(stage)` and merges the stage's histogram files per weight with `merge.merge_histograms`. It finds the files at run time: the first pattern in `HISTOGRAM_NAMES` of which seed 1 has a file, and the weights from seed 1's files. `complete()` is false while the timings task is incomplete, and true without any files (stage 2 without `testplots 1`). It has its own `job_name` and log dir (`<stage>-merge`). Its `batch_job_is_hung()` returns False: it overrides the one inherited from `POWHEGStage`, which b2luigi would otherwise call and which would read the POWHEG log of the stage's seed 1.

## Invariants that are easy to break

- **The config dict must be reproduced exactly inside batch jobs.** Each job runs `<config python> -m powgatory --config_file <file> <b2luigi args>` from the submit-time `cwd` (see `executable_prefix`, `executable`, `task_cmd_additional_args` and `working_dir` on `POWHEGStage`). b2luigi then rebuilds the whole task graph in the job and looks the task up by `task_id`. Because `config` is a hashed `DictParameter`, every value in the dict has to come out identical in the job. That includes `cwd` and `python` (from `sys.executable`). Otherwise the job fails with "task id ... does not exist in the locally reproduced task graph". Nothing queried from Slurm may go into the dict: the partition table (`slurm_partitions()`) and `scontrol show config` (`slurm_config()`) are cached module functions, read only by the process that starts the run (partition validation in `cli.py`, `POWHEGStage.partition_info`/`tasks_per_node`/`max_grouping_size`/`slurm_settings`), so batch jobs, and every rank of an MPI job, send no request to the Slurm controller. The same goes for `version`, which is `__version__` with dots replaced by hyphens, so a version bump changes every task ID. `POWHEGConfig.__init__` has side effects (it creates directories and prints the config), and these run again in every batch job, so it must not write files that other jobs read.
- **Completion is based on files, not exit codes.** `POWHEGStage.output()` returns several alternative sets of POWHEG output files: 4- and 5-digit seeds (`seed_strings`, used for every seed in a file name), and for stage 1 also the `pwggridinfo-*` variant. `complete()` accepts any one set. `_wait_for_stage_output` and `_quarantine_stale_outputs` both work from `output()`. The latter moves leftovers from a previous attempt into `incomplete_run_backups/` before POWHEG runs again. For stage-3 seeds (grid combination and stage 3), this includes the `*-fullgrid.lock` files that contain the seed's own number (`_own_fullgrid_locks`). POWHEG's `pwhg_exit` deletes its locks, so such a lock can only be left by a killed earlier attempt of the same seed. Locks of other seeds must never be touched, because those seeds may still be running. Rerunning `powgatory` resubmits only the branches that are incomplete.
- **Log markers.** `_run_program` writes `<Started-POWHEG:<job_code>=<iso time>>` and `<Finished-POWHEG:...>` into each branch log, and `POWHEGStageTimings._parse_log_timing` parses them. Change both together. `POWHEGStageTimings.complete()` also checks that its dependencies are complete, so an entry left in `timings.yaml` by an older run does not count.
- **b2luigi settings are task properties.** `POWHEGStage` provides b2luigi settings (`batch_system`, `submission_type`, `max_grouping_size`, `slurm_settings`, `result_dir`, `task_file_dir`, `job_name`, ...) as properties that read the per-stage config, because `b2luigi.get_setting` looks at the task first. Add new per-stage settings the same way. The setup, symlink, presubmit and timings tasks set `batch_system = "local"`.
- **Stuck and lost jobs are handled by b2luigi** (`slurm_resubmission`). `POWHEGStage` supplies `slurm_max_resubmissions` (`job_settings.retries`), `slurm_completing_grace` (`job_settings.completing_grace`), `slurm_hung_check_after` (`job_settings.hung_start_minutes`) and the hook `batch_job_is_hung()`, which reads the branch's POWHEG log. b2luigi's `SlurmJobState` counts a job in COMPLETING or lost as successful if the branch's outputs are complete. Otherwise it resubmits a lost job at once, and a job in COMPLETING after `completing_grace` seconds. It asks `batch_job_is_hung()` once, `hung_start_minutes` after it first saw the job RUNNING, and cancels and resubmits a hung job. `POWHEGBaseTask.retry_count` is 1, so luigi never retries, and a POWHEG failure is never rerun automatically.
- `complete()` and `_wait_for_stage_output` share `_complete_output_set`: a branch is complete only if every file of one output set exists and is non-empty. On a POWHEG error, `_run_program` moves the branch's outputs aside, because `pwhg_exit` writes the counters file also on failure.
- `setup_container` runs inside every batch job. `POWHEGPresubmit` calls it once beforehand, so a local `container_image` is copied and a registry image pulled to `<run_dir>/powheg.sif` before any stage runs: when the parallel jobs of a stage copied it themselves, jobs started apptainer on a half-written copy. Keep the call in `POWHEGStage.run`, for runs whose seeds do not share one run directory. With `job_settings.copy_container_image: false`, a local image is used in place, so that many runs share one image.
- `cli.py` locks every run directory in the main process (not in batch jobs, which carry `--batch-runner`), so that two POWgatory processes never share a run directory. A lock is one byte of `<parent>/.powgatory-run-dirs.lock`, at an offset from the sha256 of the run directory's name (POSIX byte-range locks, `fcntl.lockf`), so all run directories of one parent share one open file: an `flock` per run directory needed one open file each, and 900 configs exceeded the login shell's soft limit of 1024. Closing any descriptor of a lock file releases all its locks, so nothing else may open these files.
- `branch_id` is a `BatchIntParameter(grouping=True)`. In a grouped submission it can be a tuple of seeds, so build names from it with `format_branch_id` or `job_code(..., format_seed=True)`.
- `addweights` exists in the config schema and validation but has no tasks yet.
